# Architecture — V0.9 Submission Candidate

Browser:
`index.html` → `data/rules.js` → `app.js`

Source of truth:
`data/rules-2026.json`

The browser copy is generated by `scripts/sync_rules_js.py`.

## Trust boundary
The approved ruleset is immutable to the automated watcher.
`scripts/watch_rules.py` can only produce `reports/regulatory_status.json`.
It has no write path to `data/rules-2026.json`.

## Change process
1. monthly check reads official HTTPS sources;
2. ambiguous/different candidates => `review_required`;
3. human review;
4. manually edit JSON if justified;
5. recalculate ruleset hash/ID and sync JS;
6. run JavaScript + independent Python regression tests;
7. commit reviewed version.

## Why two test engines?
The Python implementation uses Decimal throughout and compares its results with the actual
JavaScript through the read-only `test_app_js.cjs --cases` bridge. CI runs both suites and
a separate semantic JSON/JS equality check; tests never synchronize fiscal files.

The small `app_harness.cjs` fixture derives its element IDs, input values, radio choices and
script order from `index.html`. It records actual event listeners and dispatches submit
to the handler installed by `app.js`; unknown IDs return null. It is not a full browser DOM.
Static HTMLParser checks cover the comparison section's ARIA association and the missing-quote regression.

## V0.9 correction boundary
The fiscal JavaScript functions, data files, stylesheet and 13/14 policy are unchanged.
Watcher changes are limited to regex escaping and its release User-Agent. F5 semantic
limitations remain as documented in README; F10 and F11 are explicitly unchanged.
The shipped regulatory report is an offline fixture, not evidence of a live technical check.
